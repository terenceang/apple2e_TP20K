# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An Apple //e implemented in Verilog for the Sipeed Tang Nano 20K (Gowin GW2AR-LV18QN88C8/I7). The build uses the open-source toolchain (Yosys, nextpnr-gowin, gowin_pack, openFPGALoader). Video and audio go out over HDMI (720x480p with 48 kHz audio in data islands), audio also through the onboard MAX98357A I2S amp, and keyboard input plus a hardware debugger run over the 115200-baud UART on the BL616 USB-serial bridge.

## Commands

```sh
make            # full build: synth -> pnr -> pack => build/bitstream/Apple_TN20K.fs
make synth      # yosys only (build/yosys/top.json)
make pnr        # nextpnr-gowin (build/pnr/top.pnr.json)
make flash-sram # load bitstream into SRAM (volatile, fast; use for iteration)
make flash      # write bitstream to onboard flash (persistent)
make clean

make web-install   # npm install in web/
make web-build     # bundle web/dist
make web-dev       # Vite dev server
make web-test      # node --test in web/
make web-charset   # build the glyph table from roms/apple2e_char.hex

scripts/build.ps1 [-Synth|-Pnr|-Pack]  # the build itself; the Makefile wraps this
scripts/prog.ps1 [-Flash]             # openFPGALoader / Gowin programmer
scripts/hdmi_diff.ps1 -Check          # src/hdmi/ still matches its snapshot
scripts/hdmi_diff.ps1 -Upstream       # what has TN20K-HDMI changed since
sim/run.ps1                           # all testbenches with iverilog
```

- **The Makefile has no build logic.** `scripts/build.ps1` is the single implementation and the Makefile is a thin wrapper, so `make` and the OpenFPGA Deck produce the same netlist at the same paths. There used to be two flows with different nextpnr flags and different output paths; do not reintroduce flags anywhere else. Every stage re-runs from scratch, so iterate with `-Synth`, then `-Pnr`, then `-Pack`.
- **New source files go in `sources:` in `fpga.yaml` only.** `scripts/sources.ps1` reads that list, and `scripts/build.ps1` (for `synth.ys`) and `sim/run.ps1` (for `tb_top`) both use it. The Makefile has no `SRCS` list and `sim/run.ps1` does not parse the Makefile any more.
- **`scripts/build.ps1` gates on achieved Fmax**, not on nextpnr's exit status: it greps `Max frequency` out of `build/logs/pnr.log` and fails the build if the worst clock is below `VM_PIXEL_HZ` (27 MHz). It passes `--freq` but not `--sdc`, matching the Deck. `constraints/top.sdc` is the stricter alternative (it declares each clock domain explicitly, including the `clk_in` -> `clk_pixel` cross-domain path) if you want the fuller analysis; the log also reports a cross-domain path.
- **Judge every native tool by its exit code, never by its stderr.** The build script runs with `$ErrorActionPreference = 'Stop'`, and PowerShell turns *any* stderr from a native command into a terminating error — so a bare `& $script:NextPnr` aborts the build on nextpnr's own `Failed to route net 'clk_pixel' ... using dedicated routing` warning, which this design always emits: `clk_pixel` comes off a `CLKDIV` output, nextpnr cannot put that on the dedicated clock network, and it falls back to general routing and says so. The nextpnr call therefore saves the preference, sets `Continue` around the invocation, merges stderr into the output so it prints as plain text, and throws on `$LASTEXITCODE`; `Invoke-Tool` in `scripts/toolchain.ps1` and the `vvp` call in `sim/run.ps1` do the same thing. **Do not "simplify" any of them back to a bare call.** Getting this wrong kills the build at pnr, before the Fmax gate and before `gowin_pack`, and leaves a stale bitstream sitting in `build/bitstream/` looking like success. The `NativeCommandError` traces `Invoke-Tool` still prints for yosys and `gowin_pack` are cosmetic only — those calls are already handled and their logs are in `build/logs/`.
- **The Makefile pins `SHELL := cmd.exe`, and `make` is only the entry point.** The recipes are cmd.exe-flavoured — `if exist build rmdir /s /q build` in `clean` is not POSIX — and GNU make silently switches to `sh` when it finds an `sh.exe` on `PATH`, which installing Git Bash or MSYS2 would do, so the pin is what keeps those recipes working. Nothing in the build needs `make`: there is no CI, and the OpenFPGA Deck invokes `scripts/build.ps1` directly. But every command above and in the README is spelled with it, so a machine without it fails on the first line of the quick start. GnuWin32 Make 3.81 is what is installed here (`C:\Program Files (x86)\GnuWin32\bin`, added to the *user* `PATH`); it ships no `sh.exe`, and the Makefile also calls Windows PowerShell 5.1 by absolute path, so `pwsh` 7 alone will not do.
- `sim/run.ps1` builds and runs all testbenches with iverilog (~80 s) and exits non-zero on failure; each testbench prints `PASS` or a line starting with `FAIL`, which `run.ps1` greps for (Icarus ignores `$finish(1)`; on Windows, `iverilog -o` writes a vvp script, so `run.ps1` runs it through `vvp`). The `$hdmi` file list at the top of `run.ps1` is checked against `fpga.yaml` on every run. `tb_video_hdmi` runs `video_generator` + `colorbar_gen` through `hdmi_tx` with `top.v`'s wiring and decodes every pixel from the TMDS lanes against an independent model of the text screen / bars (it catches a one-pixel look-ahead error). `tb_sound` checks the I2S frame rate and the 1 kHz test tone. `tb_input` drives the 115200-baud receiver with real bit timings and checks the host protocol end to end: legacy ASCII, the `FE` key packet with its paddle buttons, the `FF` gamepad packet, ANSI cursor keys, and `0x02` never reaching the keyboard. `tb_top` runs the whole `top.v` on `sim/models/gowin_prims.v` (behavioral `rPLL`/`CLKDIV`/`OSER10`/`TLVDS_OBUF`; Yosys' `cells_sim.v` has only empty shells for these, and no `CLKDIV`), checks the pins replay `hdmi_tx`'s symbols and that HDMI audio runs at 48 kHz; it needs the ROMs. `tb_video_hdmi` uses a *synthetic* char ROM (distinct data per address row), so it checks glyph *addressing*, not the real character set — nothing testbench-verifies `roms/apple2e_char.hex`'s contents, and the polarity and bit order of the real ROM are pinned instead by `web/test/charset.test.js`.
- The HDMI core `` `include``s `src/hdmi/hdmi_defs.vh` by repo-relative path, like the ROM paths, so run tools from the repo root. The UART bit-rate divisor is likewise single-sourced in `src/uart_defs.vh`, included by both `input_controller.v` (RX) and `serial_debugger.v` (TX).
- ROMs are gitignored (Apple copyright), so a fresh clone needs the user to supply them; see `roms/README.md`. ROMs are loaded with `$readmemh` using paths relative to the repo root (`roms/apple2e_rom.hex` is 16 KB covering $C000–$FFFF; `roms/apple2e_char.hex` is 4 KB, the 2732 — its size must match `apple2_char_rom`'s `mem[0:4095]`, since `char_rom_addr` is only 12 bits). Run tools from the repo root.
- **The character ROM is addressed with 6 bits of the character code**, not 7: `char_rom_addr = {1'b0, code[7]|(code[6]&flash), code[6]&code[7], code[5:0], glyph_row}`, so `$41` reads glyph 1 and bits 7/6 only select the alternate set. **A CLEAR bit in the ROM is a lit dot** (`pixel_on = ~glyph_byte[dot]`; the 2732 is active-low). Normal glyphs (the 0x400/0x600 halves, codes `$80-$FF`) are stored complemented, e.g. `$C1` reads `F7 EB DD DD C1 DD DD FF`, and space is all `FF`; the inverse half (0x000, codes `$00-$3F`) is stored the other way round so the same `~` draws it dark on light. **Do not judge polarity from glyph 0 at address 0** — that is the inverse half, and reading it as "1 = lit" is what made the screen green with black text on hardware. `web/src/charset.js` `dotRow` is `~romByte`, and `web/test/charset.test.js` and `tb_video_hdmi`'s real-ROM check pin normal codes (`$C1`, `$A0`); change one side and they tell you.
- **The app talks to the board over Web Serial directly.** With the board plugged into the machine running the browser, `serial-link.js` opens the port directly and nothing needs installing — in Chrome/Edge, in a secure context (https or localhost), and from a user gesture, which is why there is a Connect button. The connection satisfies the `Link` interface and moves raw bytes in both directions. **The FT2232C has two channels and only one is the FPGA's UART** — they are indistinguishable in the device picker, so the choice is confirmed by asking the debugger (`02` then `?`, looking for the help line) and the wrong one is reported and closed. Keep that handshake; it is the only thing that tells the two apart.
- **Publishing the page.** GitHub Pages for this repo can only be served from a branch root or `/docs`, so `web/scripts/pages.mjs` builds the bundle, checks it, and copies it to `docs/`, which is the site's root (`https://terenceang.github.io/<repo>/`). **Everything in `docs/` is published**: the board documentation lives in `Documents/` precisely so it is not, and the script refuses to run if `docs/` holds anything it did not put there. Three things the check enforces: the published bundle must not contain the Apple 2732 (`charset.js` inlines `generated/charset.json`, and a Pages site is public the moment it is published, the same reason `roms/*.hex` is gitignored — `PAGES=1` in `vite.config.ts` aliases that import to `src/generated/no-charset.js`); asset paths must be relative, because a project site is served from `/<repo>/`; and no sourcemap. It exits non-zero and copies nothing if any of that fails; do not weaken it to a warning.
- **`web/src/keymap.js` is the Apple //e keymap and is tested as the era check** — `web/test/keymap.test.js` fails if a REPT key, function key, numpad, `⌘` or a Mac `*:` key appears, and asserts the reachable character set is exactly the //e's 40-column repertoire. Do not "fix" the keymap by adding keys without checking that test. The physical arrangement is data in `web/src/keyboard/layouts.js`.
- **`web/` is a separate Node project** and the only JS in the repo. It is a front end over the same UART, not part of the FPGA build: `make web-*` targets are the entry points. Its logic is all testable from node with no browser, because Web Serial is injected rather than reached for globally.
- The host protocol is documented in `web/README.md` and in the header of `src/input_controller.v`: `02` toggles the debugger and is dropped before the keyboard sees it; `FE <code> <btns>` is a keypress with the paddle button state; `FF 01 <btns> <x> <y>` is the gamepad; `1B 5B A|B|C|D` are the cursor keys; `FF 04` is all-keys-up (drops any-key-down, `$C010` bit 7: an `FE` key holds it until this arrives, a plain ASCII key drops it after ~100 ms); `FF 03 <btns>` is the RESET key (bit 3 = held, bits 0-2 = paddle buttons; the app sends it only with Ctrl down, as on a //e); anything else is a plain ASCII keystroke. `<code>` is the **final** character, because a real //e's keyboard PROM (341-0132-D) resolves shift and caps lock before `$C000` and the ROMs take D6-D0 as final — so the app, not the RTL, owns the shift/caps logic, and `input_controller` stays a plain latch.

## Architecture

The design runs almost entirely in one clock domain. `clk_gen.v`'s rPLL turns the 27 MHz crystal into `clk_tmds` (135 MHz, 5× pixel clock), and `clk_pixel` is then derived from `clk_tmds` via a `CLKDIV` (divide-by-5) rather than tapped directly off the crystal — the HDMI `OSER10` serializers need a fixed, drift-free phase relationship between `clk_pixel` (PCLK) and `clk_tmds` (FCLK), which only a shared hardware divider off the same PLL output guarantees; feeding OSER10 two independently-routed clocks (frequency-locked but not phase-locked) causes the display to intermittently drop in and out of sync.

**Clock enables, not clocks.** `clk_gen.v` makes `ce_1m` (1.0227 MHz) and `flash_clk` (~1.6 Hz) from 32-bit/24-bit phase accumulators. The 65C02 is clocked at 27 MHz but gated by `RDY = ce_1m & cpu_rdy` (called `cpu_go` in `apple2_core.v`), and all softswitch and I/O logic is qualified by `ce_1m`. Keep new CPU-visible logic in this pattern.

**Shared RAM time multiplexing** (`apple2_core.v`): the 64 KB RAM is a single-port BRAM (`apple2_ram_64k` in `apple2_mem.v`). On cycles where `ce_1m=1`, the CPU (or the debugger) owns the address bus. On all other cycles the video generator's `vram_addr` is used, and `vram_data` is latched from those cycles. Video therefore sees RAM with a one-cycle registered latency, and `video_generator.v` prefetches the next column (`fetch_col`) to allow for this.

**Memory map / decode** (`apple2_core.v`): $0000–$BFFF main RAM; $C0xx I/O; $C100–$CFFF internal ROM; $D000–$FFFF language card (ROM or RAM, with the //e bank-switch semantics at $C080–$C08F). **The peripheral bus is in `src/slot_bus.v`** (see the Slot bus section below): the per-slot decode, the $C800 expansion-space claim, and the interrupt wiring, with no cards installed, so $C100–$CFFF still answers the internal ROM when a softswitch selects it and reads $00 in an empty slot. Aux RAM (RAMRD/RAMWRT/ALTZP, 80STORE+PAGE2, and the $C013-$C017 status reads) is the second 64 KB, held in the board's SDRAM, not BSRAM (`src/aux_ram.v` around the vendored `src/sdram/sdram.v`, which is **GPL-3**, Till Harbaum's controller from MiSTeryNano; pins in `constraints/top.cst`). The video never reads SDRAM: `aux_ram` fills a 40-byte line buffer during each scanline's blanking (`aux_fill_*` from `video_generator`), the CPU has a one-word read cache and a one-entry write buffer, and `apple2_core` stalls `cpu_ce` (`aux_stall`, folded into `video_busy`) only on a cache miss or a busy write buffer. The debugger sees main RAM only. 80-column text fetches aux then main per 14-clock slot (`wide` in `video_generator`); Double hi-res (`dhires`, $C05E/F, with 80COL and HIRES) uses the same two-byte slot with the aux byte first and feeds the same NTSC window one sample per clock; its aux bytes come from the hi-res line of the next scanline (`aux_fill_addr`). ALTCHARSET reads the $200 block of the same 4 KB 2732 for $40-$7F (MouseText and inverse lowercase, no flashing), so it costs no BSRAM: `char_rom_addr` bits are `{0, c7 | (c6 & flash & ~alt), c6 & (c7 | alt), code[5:0], row}`. `sim/tb_aux_ram.v` runs the controller against `sim/models/sdram_model.v`; the vendored file needs `-sv` in synthesis (`scripts/build.ps1`) and `gen=2012` in `sim/run.ps1`. Verified on the board: aux and main $0300 hold different values, read back through the SDRAM. To test aux, run machine code from the stack page (BASIC's own program text would be fetched from aux once RAMRD is on).`cpu_din` is a combinational mux: `input_controller` claims $C0xx reads through `io_hit`/`io_dout` (keyboard $C000/$C010, pushbuttons $C061–3, paddles $C064/5, $C070), `u_slot_bus` claims $C100–$CFFF through `slot_int_rom`/`slot_dout`, and the core supplies $C011–$C01F status reads.

**Debugger path** (`serial_debugger.v`): pressing Ctrl+B (0x02) on the UART toggles `dbg_mode` and drops `cpu_rdy` to freeze the CPU. While paused, `effective_cpu_addr` switches to `dbg_mem_addr` so the debugger can read memory through the same `cpu_din` mux (`dbg_mem_din`). Commands are r/s/c/g/m/t/w/h/?/x, `y` (mount a TF card slot on the slot 7 hard disk, see Hardware notes), plus `i` (prints `I1:xxxxxxxx I2:xxxxxxxx`, the Disk II drives' image checksums, 0 = empty: a rotate-left-1-and-add over every uploaded byte, cleared at the start or loss of an upload and by `n1`/`n2`, which eject a drive (`img_up_bad` for it, one clock after `img_drv`); **a reset does not take the disks out** (the images are in DDR3 and survive it, so `disk2_store` keeps `present` and the debugger its sums), and with no disk in either drive the slot 6 ROM reads as `$00` (`d2_any_disk` in `apple2_core`), so a cold boot falls through the Autostart scan into BASIC; `web/src/disk.js` `diskChecksum` is the same sum, which is how the page learns what the board holds and skips re-uploading an identical image) plus `0 1 4 8 f v` to set the dump address, and `a` to toggle the aux RAM view (`m` then prints `;` after the address and `w` sets bit 7 of its flags byte; aux reads are slow, so the debugger waits on `dbg_mem_ready`); **they are only consumed when `main_state == M_IDLE`, and anything sent earlier is dropped without a word** — and the banner prints two prompts (one at the end of the banner string, one after the register dump), so a host that paces on the prompt will still lose commands. `web/` paces on 200 ms of silence instead. `w` (M_SCREEN) dumps the whole 1 KB text page in memory order (interleaving holes included; the host applies the row interleave via `textPageIndex`) plus lo-res rows 20-23 of the same page ($250/$2D0/$350/$3D0 offsets — what the bottom four lines show in mixed-mode graphics; with 80STORE+PAGE2 the displayed page is aux, which the debugger cannot read, so the dump shows the main-RAM copy), and is only reachable while paused, which is what makes the read race-free — there is no spare bus to read $0400 while the CPU runs. In console mode the debugger echoes received bytes back, filtered to printable plus CR/LF/BS/BEL so the `FE` and `FF` packets do not land in the console as junk. `input_controller` owns the UART RX and passes `rx_byte`/`rx_valid` to the debugger; it drops keystrokes while `dbg_mode` is set. It also turns ANSI arrow-key escape sequences into Apple control codes.

**Video** (`video_generator.v`): the Apple 560×384 raster (192 lines doubled, 14 px per column) is centered at x=80..639, y=48..431 of the 720×480 frame, and `vbl` feeds $C019. The generator handles the Apple interleaved row addressing for text, lo-res and HGR (page 1 $2000 / page 2 $4000, mixed mode keeps the bottom four lines on the text page). HGR reuses the text pipeline: one byte per 14-px slot, 2 px per dot, and the bit-7 half-dot delay is one clock. Colour is an NTSC-style decode of the 560-sample dot stream: each pixel takes the window s[n-2..n+1] (4 samples = one subcarrier cycle), luma = lit count, I/Q from the sample phases (`n mod 4`), so solid fills, fringes and the bit-7 blue/orange come out of the stream rather than a palette rule. `tb_video_hdmi` checks every pixel against an independent model and pins the solid-line colours. It has no timing of its own: `hdmi_tx` owns the raster and samples `video_rgb` combinationally for its `(pixel_x, pixel_y)`, and because the generator's colour output is registered, `top.v` feeds it the *next* pixel (`h_cnt = pixel_x + 1`, `v_cnt = pixel_y`). `h_cnt` must step by one every clock (its column counter and RAM prefetch count clocks). Anything new that drives `hdmi_rgb` must honour the same same-cycle contract (`colorbar_gen` is combinational on `pixel_x`/`pixel_y`).

**HDMI** (`src/hdmi/`): a local copy of the HDMI transmitter from the TN20K-HDMI project (both are yours, both MIT), taken at commit `388b39e`. It is a copy rather than a submodule so this repo builds with nothing else checked out beside it, and it is not kept in step automatically — treat it as a snapshot, not a fork to merge. `scripts/hdmi_snapshot.sha256` records exactly what it is, and `scripts/hdmi_diff.ps1 -Check` fails if any file is edited locally without re-baselining; `-Upstream` shows what TN20K-HDMI has done since. The only deliberate local change is `hdmi_tx`'s `RGB_QUANT` parameter (see below); everything else is byte-identical. `~/TN20K-HDMI/CLAUDE.md` documents the internals in more depth than this file does.

`hdmi_tx` does CEA-861 720×480p59.94 (VIC 2) timing, the TMDS encoders (fixed 2-cycle latency in every mode, which the island scheduler's alignment depends on), and data islands carrying Audio Sample Packets, ACR (N=6144, CTS=27000), and the AVI and Audio InfoFrames. Mode and audio constants are in `hdmi_defs.vh`. The local `RGB_QUANT` parameter is the reason for the copy: `top.v` sets full range (`2'b10`) in the AVI InfoFrame because the Apple palette is 0–255, and a CE-mode sink would otherwise assume limited range and crush blacks. The `OSER10` + `TLVDS_OBUF` serializers are a generate loop in `top.v`; lane 3 is the TMDS clock (`0000011111`). `TLVDS_OBUF` is required on pins 33-40 (apicula rejects `ELVDS_OBUF` there with "it is a true lvds pin"), with `IO_TYPE=LVDS25` and one single-pin `IO_LOC` per leg in the `.cst`; the Tang Nano 9K's GW1NR-9 needs emulated LVDS instead, so don't copy that board's HDMI code here. The HDMI link has its own reset (`hdmi_rst_n`: PLL lock plus 128 pixel clocks), independent of `sys_reset`, so S2 resets the Apple without the display re-syncing.

History: an earlier HDMI-audio attempt using Sameer Puri's hdmi.sv packet library worked briefly, then reset the whole board once data-island activity ramped up (suspected power/timing margin in the much larger design). If the board resets or the link drops with this core, suspect that first. Holding S1 swaps only the picture (data islands and audio keep running), so it separates the Apple core from the HDMI link but not audio from video. Diagnose with a scope/logic analyzer rather than blind hardware iteration.

**HDMI bring-up test pattern** (`colorbar_gen.v`): holding `btn_s1` (active-high, pulled down by board 1k resistor) forces `top.v`'s HDMI mux to an 8-bar color pattern with a border and a blinking liveness box, independent of the CPU/RAM/`video_generator`, plus a 1kHz test tone (`sound_generator.v`'s `test_tone_enable`) on the I2S speaker and HDMI audio — use this to isolate the clocking/serializer/display chain from the rest of the design when video misbehaves.

**Audio** (`sound_generator.v`): any access to $C03x pulses `spkr_pulse`, which toggles the speaker flip-flop. That drives a damped-impulse sample model sent out over I2S. `audio_sample` updates once per 64-BCLK frame, and the frame rate is **exactly 46.875 kHz** because 27 MHz / 46.875 kHz is exactly 576 clocks and 576/64 = 9 clocks per BCLK. 9 is odd, so `bclk_div` free-runs 0..8 and toggles BCLK at both 4 and 8 (4 high, 5 low). A single toggle compare gives an even period, lands on 42187.5 Hz, and puts the 1 kHz test tone out at ~900 Hz. The same sample is resampled at 48 kHz by a fractional accumulator in `top.v` and sent over HDMI as stereo L-PCM, so the two rates are coupled: change one and you must change the other. `sim/tb_sound.v` checks the BCLK period, the frame interval and the tone frequency. `test_tone_enable` (wired to `btn_s1` in `top.v`) substitutes a 1kHz square wave for bring-up testing.

**Block RAM is the scarce resource, not LUTs.** This device has 46 BSRAM and the design uses 42 of them (64 KB RAM = 32, system ROM = 8, char ROM = 2, plus small ones), against 6780/20736 LUT4 and a `clk_pixel` Fmax of ~70 MHz against a 27 MHz target. Adding a memory means finding BSRAM first; logic is nearly free. The char ROM is 4 KB rather than 8 KB precisely to keep two BSRAM blocks free, and `char_rom_addr` is only 12 bits.

**CPU** (`src/cpu/`): Arlet Ottens' 6502 core with the 65C02 extensions by David Banks and Ed Spittles. It has been modified to expose `debug_*` register ports. IRQ and NMI come from `slot_bus`, which drives them inactive while no cards are installed (they were tied low directly before).

**Slot bus** (`src/slot_bus.v`): the //e's peripheral architecture, motherboard half only — there are still no cards, so this is scaffolding for them, not a working slot. It decodes the real bus rules so a card is later a matter of driving the card-side inputs rather than re-deriving the //e's address and interrupt semantics inside `apple2_core`: `/DEVSEL` for $C0n0-$C0nF (slots 1-7 only; $C080-$C08F is the language card and $C090-$C0FF is slots 8-15's space, which a //e has no cards in, so neither strobes), `/IOSEL` for $Cn00-$CnFF, the $C800-$CFFF expansion space with its claim latch (a card with `card_exprom` claims it on `/IOSEL` and holds it until the `$CFFF` `/IOSTROBE` pulse; `intc8rom` outranks a card, as on a //e), and the interrupts: `/IRQ` as a daisy chain from `int_in_n` through slots 1-7 where a populated slot only passes the chain on if it is not asserting, `/NMI` and `/DMA` as shared wired-OR lines (not chained; the 65C02 does its own NMI edge detection). The read-bus arbitration it returns to `apple2_core` is the expression that used to be inline in the `cpu_din` mux (`intcxrom || (C3xx && !slotc3rom) || (>= C800 && intc8rom)` for the internal ROM, else the addressed card's byte, else $00 for a floating bus), so behaviour with no cards is bit-identical. `sim/tb_slots.v` drives `slot_bus` directly with fake cards — the card side is only ever tied inactive otherwise, so nothing in the design would exercise the decode — and `tb_auxsw` checks the same rules through `apple2_core` with no cards. Its idle levels are named (`LINE_IDLE`, `NO_DATA`) because the obvious typo, `7'd7`, is decimal seven and leaves slot 4 asserting a line it has no card for; the bench was checked by reintroducing each of its three past bugs to confirm the checks are not decorative. It costs 5 LUT4, no BSRAM, and no pins.

**Disk II** (`src/disk2/`): `disk2_card.v` synthesises the slot-6 byte stream (440 bytes per sector, `SECT_LEN` is the one place that length is written) and `disk2_store.v` keeps the 2 x 143,360-byte images in SDRAM bank 1, answers the card's per-position six-bit value requests and decodes written data fields back into SDRAM. **Everything the two must agree on lives in `gcr_defs.vh`**: the 6-and-2 and 4-and-4 tables, `gcr_pair_swap` (the bit transposition the P6 ROM unpacks) and `gcr_aux_src` (which sector bytes an auxiliary position carries). Do not copy any of it into either module. The card reports where the head is once, as `pos_sec`/`pos_track`/`pos_drive`, and both the group request and the write capture use that. `web/src/disk.js` owns the image order (`DOS_TO_PHYS`, with `PHYS_TO_DOS` derived from it) and the `d`/`e`/`p`/`o` transfer protocol, which `sendImage`/`receiveImage` implement once for floppy and hard disk. `tb_p6boot` takes ~45 min and, as of the 2026-10 review, stalls at PC `$c3fc` in simulation on HEAD too (hardware boots DOS 3.3); run `tb_disk2` and `tb_diskimg` for the Disk II path.

**ESP32 companion (`DSK_TRK`, branch ESP32-Companion)**: `localparam DSK_TRK` in `top.v` (passed to `apple2_core`) selects the Disk II path. `0` is the sector card above; `1` swaps in `src/disk2/disk2_trk.v` + `src/spi_ctl.v` + `src/spi_master.v` and the debugger's `d/e` upload has nothing to talk to. In that mode the image is not synthesised in the FPGA at all: an ESP32 (`mcu/`, PlatformIO + ESP-IDF, classic ESP32) encodes each track into the card's own 7040-byte nibble stream (`web/src/nibble.js` is the reference, `mcu/src/nibble.c` the C port; `build/golden_track0.hex`, written by `sim/tb_disk2.v`, pins both byte for byte), `spi_ctl` loads them into SDRAM bank 1 (slot layout in `src/disk2/trk_defs.vh`, 7168 B per track so it fits the 19-bit byte address `sd_word_addr` uses), and `disk2_trk` plays/overwrites bytes there. The card keeps the byte-per-33-`ce_1m` model, so no bit-level player yet (that is the WOZ phase). A written track is flushed to the ESP32 (`WRITE_TRK`) once the head leaves it or the motor stops, and the ESP32 decodes sectors back into the image on its SD card. Link: SPI mode 0, FPGA master, SCK 73 / MOSI 74 / MISO 77 / CS 85 (77 is the LCD clock pin and 85 microSD DAT1, both unused here; 75, the BL616 SPI MISO, is avoided), 6.75 MHz (`HALF=2`; 13.5 MHz is over the ESP32 slave's limit). Protocol is documented at the top of `src/spi_ctl.v`; `sim/tb_spi_ctl.v` has a behavioural ESP32 that is the executable spec, and mutating the pairing in `spi_ctl` or the half-select in `disk2_trk` makes it fail (checked). ESP32 pins: FPGA link on VSPI 18/23/19/5, SD card on SPI2 25/26/27/32 (clear of the strapping pins). Host C test: `python -m ziglang cc -o build/test_nibble.exe mcu/test/test_nibble.c mcu/src/nibble.c` (zig via `pip install ziglang`, there is no gcc here). Firmware layout: Disk library: images live in `/sd/disks/` under any name (`disk_name_ok`: letters, digits `. _ -`, a `.dsk/.do/.po` extension, 31 chars), the web page adds, mounts (drive 1 or 2), ejects and deletes them, and **which image each drive holds is kept in NVS (`disks` namespace, keys `d0`/`d1`) so it survives a reset; eject is remembered too**. One image cannot be in both drives (one writer per file); replacing a mounted image by uploading the same name remounts it. `mcu/src/disks.h` is the one home for `SD_MOUNT`, `DISK_DIR`, `DISK_TRACKS`, `DISK_BYTES`, `DISK_EXTS` and `disk_path()` (`web.c` and `main.c` use them, do not respell `/sd/disk%d.%s` or `35*16*256`); `link.c` has the opcode enum and `ACK`, and its job queue is `NWBUF - 1` deep because the worker holds one more write buffer outside the queue (queue depth `NWBUF` let a burst of track writes overwrite a buffer still being decoded). `DOS_TO_PHYS` and the GCR tables are repeated in C, JS and Verilog; only the GCR tables are pinned (by the golden track), `DOS_TO_PHYS` is not. `OP_HELLO`/`OP_STATUS` write the response buffer the `READ_TRK` worker also uses, which is safe only because the FPGA waits for each answer before sending the next command. `mcu/src/oled.c` drives a 128x64 SSD1309 on I2C (SDA 21, SCL 22; probes 0x3D then 0x3C, logs and carries on if absent) with a one-second status screen: both drives, SD ok/missing, Wi-Fi IP; it builds but is untested on the display. Wi-Fi: the board is always its own access point (`Apple-XXXX`, password random per board, kept in NVS) and also joins a router when `credentials.h` exists; the OLED alternates the status page with a Wi-Fi QR code for that AP (`mcu/src/qr.c`, version 3 / ECC L / mask 0 only, checked cell for cell against Python's `qrcode` by `python test/test_qr.py` from `mcu/`), shown only while no router is joined, or for 30 s after the web page's "Show Wi-Fi QR on display" button (`POST /qr`) or a press of the DevKit's BOOT button (GPIO0, an ordinary input once running); the web page is the main control; the soft AP is the "direct Wi-Fi" link, since the ESP32 has no Wi-Fi Direct/P2P; then browse to `http://192.168.4.1/` for the mount/eject page. Wi-Fi now links in, so the app is ~950 KB (the 0x180000 partition holds it; PlatformIO's "1 MB" figure is just its default). Build/flash from `mcu/`: `pio run`, `pio run -t upload --upload-port COMxx`. The board is an ESP32 DevKit V1 (here COM44), which has no reliable auto-reset: **hold BOOT, tap EN, keep holding BOOT until `Writing at...` appears**, otherwise esptool reports `Wrong boot mode detected (0x13)` (a ~10 uF cap from EN to GND fixes it for good). Flashed and hash-verified; not yet verified on hardware: the SPI slave's frame handling, SD, and booting DOS from `DSK_TRK=1`.

## Hardware notes

- **Slot 7 is a ProDOS block device with two 32 MB volumes, kept on the TF card** (`src/prodos_hd.v`, `src/sd_vol.v`, `src/spi_byte.v`; the older 2 x 2 MB SDRAM card is in `archive/prodos_hd/` and is not this one). The volumes are served from the top half of the DDR3, two bytes per 16-bit word (`aux_ram` `hd_*`, word address `{drive, block, word}`, byte enables, lowest priority). **There is no block buffer** (BSRAM is 46/46): `$C0F0` streams to and from the DDR3, a read handing over the byte fetched last and asking for the next, which works only because the driver's copy loops leave ~14 us between bytes; `tb_prodos_hd` fails if a request ever arrives while one is out. The ROM (LUT, listing in the file header) has the ProDOS signature with `$C707=$3C` (non-zero, so not a SmartPort), driver at `$C729` (`$C7FF`), `$C7FE=$17` (two volumes; `$C0F5` selects the drive from the unit's bit 7); its boot reads block 0 of drive 1 through the driver and with no volume goes on with the Autostart scan (`JMP $FABA`, the enhanced ROM's SLOOP; `$01` still holds `$C7`), not `JMP $C600`, since slot 6 is blank when it has no disk. The Autostart ROM scans slots 7 to 1, so **with a volume in drive 1 it boots the hard disk, not the floppy** (`PR#6` for that). **The TF card is raw, no file system**: sector 0 is the config (`A2HD`, drive 1 slot, drive 2 slot, 16-bit LE, FFFF = empty) and slot N is sectors 2048 + N x 65,536; `scripts/sdvol.py` (`init`/`list`/`write`/`read`/`mount`, self-check `python scripts/test_sdvol.py`) prepares it from a PC. At `sys_reset` `sd_vol` brings the card up in SPI mode (SDHC/SDXC only), reads the config and streams each drive's slot into the DDR3 with one CMD18, and **top.v holds the CPU (`cpu_rdy & !hd_loading`) until that is done**: ~20 clocks a byte at 13.5 MHz, so ~25-35 s for a whole 32 MB volume (no card, or a DDR3 that never calibrates, gives up so the CPU still runs). Writing byte 511 of a block queues it for the card (`wb_go`) and the card's busy covers the CMD24, which the driver's WRITE waits on. The debugger's `q<hhhh>` copies an image into a slot through the board (the web page's "Copy image to slot", `disk.js` `copyToSlot`): records `01`+512 bytes, `00 hi lo` = (hi:lo)+1 zero blocks, `02` = end, one `06` per record once it is on the card; each byte goes straight from the UART to the SPI engine (`sd_vol` `x_*`), so the serial link is the limit (~48 min for a full 32 MB volume), and a drive holding that slot reloads it at the end (`x_fin`). The digits after `q`, `y` and `n` must not start a memory dump (the `mem_preset` guard). The debugger's `y<d><hhhh>` mounts a slot (rewrites the config, then loads; FFFF ejects; one slot is never in both drives), and `i` ends with `V1:ssss V2:ssss S:xx` (S = `{loading, busy, err, estage[2:0], present[1:0]}`), which `web/src/disk.js` `parseHdStatus`/`mountHd` use. TF pins on the SOM: CLK N10, CMD/MOSI R14, D0/MISO M8 (needs `use_sspi_as_gpio`), D3/CS N11. `tb_prodos_hd` boots the real ROM into a block 0 that calls the driver (needs `roms/`); `tb_sdvol` runs `sd_vol` against `sim/models/sdcard.v` (from the archive, plus CMD18/CMD12, and it folds slot 1 down so a 4 MB model holds both) on 4-block volumes (`LAST_BLK`). Not yet run on hardware.
- **The 65C02 core's `IRQ` and `NMI` inputs are active-HIGH; the slot bus is active-low.** `apple2_core.v` inverts both (`.IRQ(~slot_irq_n)`). Wired straight through, an idle bus read as a permanent IRQ, which DOS 3.3 never noticed (it never does `CLI`) but ProDOS does, and it died with `RESTART SYSTEM-$01` (ProDOS's *unclaimed interrupt* death after 256 spurious IRQs, `LDA #$01 / JSR $BF0C` in the kernel's interrupt dispatch).
- **Debugger additions for bring-up** (`serial_debugger.v`): `@xxxx` (four lowercase hex digits) sets the dump address for `m`, so any address is reachable (language-card RAM or ROM per the current switches; internal ROM shows at `$C1xx-$CFFF` when INTCXROM is on, not the cards); `k`/`j` are presets for `$E000`/`$D000`; `p` prints the last 32 opcode-fetch addresses, frozen when the PC reaches the trigger set at the `ph_frz <= 1'b1` line (edit that address and rebuild to chase a different event), and un-freezes itself after printing. Mind the console/debugger toggle when scripting: `02` flips it, a stray `C` in debugger mode means "continue", and scripts should wait ~1 s after each toggle.
- **The TF card holds the slot 7 hard disk's volumes, raw** (see above). The FAT32 layer and file manager from the Nano port are still in `archive/sdcard/` (start with its `README.md`) and are not built; `src/spi_byte.v` and `sim/models/sdcard.v` came from there.
- The pin assignments live in `constraints/top.cst`. The Tang Nano 20K LEDs are active-low. Their mapping is listed at the bottom of `top.v`: heartbeat, PLL lock, reset, CPU write, text mode and key strobe.
- `btn_s1` (active-high, pulled down) holds the HDMI/audio output on the color-bar test pattern (see above). `btn_s2` (active-high, pulled down) triggers a clean manual reset. Automatic reset also runs via the power-on counter in `top.v`.
- **Driving the board over UART for tests.** After a bitstream load the ROM sits at the Monitor `*` prompt, not Applesoft: type `E000G` to get `]`. Type BASIC at ~30-50 ms per character and wait for each line to finish before the next, because the keyboard latch is one key deep and drops keystrokes. The FPGA is the FT2232's `/dev/ttyUSB1` here (confirm with the debugger handshake). Gotchas: `GR` does not clear PAGE2 (`POKE -16300,0` returns to page 1, and the debugger's `w` dumps the page being displayed); the debugger `m` auto-increments and its first line is `+$10`, so `0` then repeated `m` walks memory; `scripts/prog.ps1` can fail once with a JTAG IDCODE error, so retry; do not use a printed string as a "program done" marker without checking it is not also in the echo of the typed line. A full HGR check is stage-by-stage photos against a render of a `$2000`/`$4000` dump (`m` over `$0000-$5FFF` takes ~20 s).
